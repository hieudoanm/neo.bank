# US-012: Handle concurrent transfers

## User Story
**As the** system,
**I want to** handle concurrent transfer requests safely,
**so that** balances remain consistent under load.

## Acceptance Criteria
- Given two concurrent transfer requests from the same account, when processed, then the system correctly handles the race condition using lightweight transactions in Cassandra.
- Given concurrent transfers that would result in a negative balance, when processed, then one transfer succeeds and the other fails with an insufficient funds error.
- The system enforces that account balances never go negative.
- Lightweight transactions ensure that debit operations check the current balance atomically.

## Technical Implementation Details

### Concurrency Control Mechanism
The system uses Cassandra lightweight transactions (LWT, also known as compare-and-set or CAS operations) to ensure atomicity and prevent race conditions.

#### Core Concept: Compare-and-Set
Cassandra LWT allows conditional updates:
```
UPDATE accounts 
SET balance_cents = balance_cents - ? 
WHERE account_id = ? 
IF balance_cents >= ? 
```
This operation succeeds only if the current balance matches the expected value (>= amount), ensuring we never debit more than the available balance.

### Implementation in Transfer Processing
When processing a transfer debit operation:
1. Read current balance and version from account record
2. Calculate new balance = current balance - transfer amount
3. Execute LWT update:
   ```
   UPDATE accounts 
   SET balance_cents = ?, version = version + 1 
   WHERE account_id = ? 
   IF balance_cents = ? AND version = ?
   ```
4. If LWT succeeds: Debit applied atomically
5. If LWT fails: Another operation modified the account concurrently - retry logic applies

### Retry Logic for Contention Handling
- **Maximum Retries**: 3 attempts
- **Backoff Strategy**: Exponential backoff (50ms, 100ms, 200ms)
- **Retry Conditions**: LWT failure due to concurrent modification
- **Non-Retry Conditions**: Actual insufficient funds (balance < amount), invalid account
- **Deadlock Prevention**: Randomized backoff timing to reduce collision probability

### Atomic Credit Operation
Similar LWT approach for crediting the destination account:
```
UPDATE accounts 
SET balance_cents = ?, version = version + 1 
WHERE account_id = ? 
IF balance_cents = ? AND version = ?
```

### Distributed Transaction Coordination
To ensure both debit and credit succeed or both fail (atomicity across accounts):
1. Process debit operation using LWT
2. If debit succeeds, process credit operation using LWT
3. If credit fails after successful debit, initiate compensation:
   - Reverse the debit using another LWT operation
   - Mark transfer as failed
4. Only mark transfer as completed after both debit and credit succeed

### Database Schema Changes
**Account Service Keyspace**
- Table: `accounts` (existing from US-004)
  - Ensure proper indexing on account_id for performance
  - Version column: bigint, used for lightweight transaction conflict detection
  - No schema changes needed from US-004, but verify version column exists and is used correctly

### Security Considerations
- Prevent balance manipulation: LWT ensures balances can never go negative regardless of concurrency level
- Fairness: No starvation guaranteed due to retry limits and backoff (extreme contention may cause failures, but not incorrect balances)
- Transaction atomicity: Either both accounts updated or neither (with compensation for partial successes)
- Audit trail: All balance changes recorded in transaction history
- No information leakage: Concurrent processing does not reveal timing-sensitive information through error messages

### Error Handling
- LWT failure after max retries: Return 503 Service Unavailable with error code `SERVICE_UNAVAILABLE` and message "Please retry your request", with a `Retry-After` header
- Actual insufficient funds after retries: Return 400 Bad Request with error code `INSUFFICIENT_FUNDS` and message "Insufficient funds"
- Invalid account during retries: Return 404 Not Found with error code `ACCOUNT_NOT_FOUND` and message "Account not found"
- Internal server errors: Return 500 with error code `INTERNAL_ERROR`

### Test Cases
1. Single transfer request → Processes successfully
2. Two concurrent transfers with sufficient funds for both → Both succeed, balances updated correctly
3. Two concurrent transfers where combined amount > balance → One succeeds, one fails with insufficient funds
4. Three concurrent transfers where any two exceed balance → At most one succeeds
5. Rapid sequential transfers → Each processed correctly with proper balance tracking
6. High concurrency scenario (100+ simultaneous requests) → System processes correctly without balance violations
7. Verify lightweight transactions prevent negative balances under all concurrency scenarios
8. Test retry logic effectiveness under contention
9. Verify exponential backoff reduces collision probability under high load
10. Test compensation logic: If debit succeeds but credit fails, debit is reversed
11. Verify no lost updates: All concurrent operations accounted for in final balance
12. Test edge case: Maximum balance (9,999,999,999 cents) with small concurrent debits
13. Test edge case: Minimum balance (0 cents) with concurrent debit attempts → All should fail
14. Verify version column increments correctly with each successful balance change
15. Test that stale version values correctly cause LWT failures
16. Verify performance remains acceptable under moderate concurrency
17. Test recovery from intermediate failure states (e.g., service restart during processing)
18. Verify no deadlocks occur under circular transfer patterns (A→B, B→A concurrently)
19. Test fairness: No permanent starvation of any request under continuous load
20. Verify system metrics accurately reflect contention and retry rates
